# Coordinated workspace finish design (#374)

## Authority and scope

Configured workspaces only. `aw finish [target] [--dry-run] [--json] [--force] [--keep-branches] [--no-hook-input]` assesses a single coordinated parent; `--dry-run` is the non-destructive preview, not a separate action. No `--no-check-dirty`, `--keep-worktrees`, `--no-hooks`, `--yes`, `--confirm-completion`, or non-interactive manual override in v1. `--force` means *discard permission* for dirty/unpublished work and consent to the ordinary remove confirmation only when completion is independently proven; it never supplies completion proof. `--keep-branches` maps to remove, default false. The command does not modify remote branches. Reject standalone mode and protected main-worktree targets.

From inside a registered coordinated parent or participating nested child, resolve the containing parent by Git worktree registration and canonical path-component ancestry, not just basename/branch. Reject multiple candidate parents, detached/uncertain identity, or explicit target conflicting with contextual parent. From main, an omitted target opens a **single-select** picker on a human TTY; an explicit path selects a registered exact parent and an explicit branch/name may fuzzy-match only if uniquely resolved to one registered parent. Ambiguity, multiple sibling worktrees with the same branch, path aliases/symlinks escaping the configured root, stale registrations and missing explicit targets fail before assessment. Non-TTY/JSON requires an explicit unambiguous target. Never expand a fuzzy match to multiple workspaces.

The participant set is the selected parent plus **all** configured child repositories with a Git-registered worktree physically contained at their configured path beneath that parent, regardless of branch. Query the complete configured inventory and check physical path identity; an existing configured child path with missing canonical clone, an unregistered Git checkout, duplicate registration, inaccessible path, or an unplanned descendant is an unavailable/ambiguous **required** participant and blocks cleanup; it is not quietly classified as nonparticipant. Configured children with no worktree at that location are nonparticipants (reported with reason); an unrelated child worktree elsewhere is not pulled in. No implied requirement that participants share a branch. Build the remove dry-run plan from the exact selected parent path (`--path`), compare its closed descendant target set with assessed participants and refuse a plan with extra/unassessed targets or omitted participants. Branch-only targets outside this exact workspace must not be deleted accidentally; validate every planned branch action, including same-named branches in other repositories, against the assessed set. If existing remove cannot express that plan safely, introduce a narrow internal exact-plan handoff, not a second removal executor. Refuse a no-op or branch-only plan. Keep this mapping under review before implementation.

## Evidence model and freshness

For each participant record canonical repo key, registered physical checkout path, branch/ref and full HEAD OID; dirty state including untracked changes; upstream full ref/OID, ahead/behind and upstream absent/unavailable; configured effective base logical branch/source (`repository-config`, `workspace-config`, or `omitted`), remote/ref/OID, and base comparison. Creation-time `create --base` / `--repo-base` and clone overrides are invocation-only and may not persist: **never label the current configured base as the historical creation base**. With no persisted base, show `omitted` and fail automatic integration verification unless an explicit, independently authenticated base policy is later added. Do not silently use the remote default branch. Include a warning if base changes since prior observation (where observable), rather than pretending history is known.

Before assessment, refresh each participant's selected base and upstream from the appropriate remote with explicit refspecs, no implicit push, pruning or tag updates; record remote URL identity, exact remote ref and fetched OID. A missing/unreachable/ambiguous ref or failed fetch is `unknown` even if stale remote-tracking refs or old `gh` results exist. No fallback to a cached base for eligibility. Fetch into an invocation-owned isolated ref/object namespace or temporary repository so preview does not change the managed workspace's worktree, local/remote-tracking refs, config, hooks or index; clean it on exit. Reuse the pinned objects for ancestry checks. The same refresh pipeline applies to normal and preview. A concurrent remote advance is not silently used as a new base. Pin inspected snapshots, then refresh and compare just before handoff and after hooks; any ref/OID/identity/config discrepancy invalidates the accepted plan rather than transparently changing the decision. Failed refresh is unknown and blocks mutation. Avoid exposing credentials or raw config/remote URL secrets in reports.

Git integration proof: `merge-base --is-ancestor <participant HEAD> <fetched effective base OID>` (within that repository) proves the exact tip is reachable; this covers ordinary and fast-forward merges, but not squash/rebase/cherry-pick equivalence. A base behind the feature head is **not** integrated. `gh` fallback only for recognized GitHub remotes: resolve the repository owner/name from the authenticated remote, query PRs including closed/merged states without relying on a limited first page, require exact head repository identity, head branch identity and **head commit OID equal to inspected local HEAD**, exact base repository and effective base ref, `mergedAt` present, and merge commit OID reachable from the freshly fetched base OID. A unique qualifying PR supplies historical integration evidence for squash/merge/rebase; report PR number, URL, mergedAt, head and merge OIDs, base ref/OID and source `github-pr`. Never correlate merely by branch name, title, patch-id, deleted remote branch or same commit message; if multiple qualifying PRs or conflicting PR metadata exist, classify unknown. Inability to establish exhaustive authenticated PR results, ambiguous forks, rate limiting, `gh` failures, other forges, or missing merge OID yields unknown. An explicit open PR whose exact head/base matches is `not-finished` unless independent ancestry proves integration; no matching PR without exhaustive evidence is unknown, not negative proof. A merged commit reachable from base documents historical integration, not immunity to later revert; report that limit and do not claim current content parity.

Unpublished state is separate from integration: absent upstream or positive ahead count is `unpublished` (even when a squash PR proves integration); upstream lookup failure is `unknown`, not zero ahead. Dirty includes staged, unstaged and untracked files; inability to inspect is unknown. `not-finished` means affirmative non-integration (e.g. exact matching open PR / committed tip ahead of fetched base with no qualifying merged proof) or an unresolved discard blocker; `unknown` means required completion/identity/freshness evidence is missing. Aggregate precedence is hard blocker/unavailable/identity ambiguity → blocked, known non-integration → blocked, unknown completion → unknown, else ready; report underlying per-repo states rather than collapsing them. An interactive human can explicitly mark **all** unknown completion cases together as manually verified, after reading repository-specific reasons, including failed fetch or an unsupported forge. This records a human judgment, not an automatic proof. It cannot override unavailable local identity/topology, observed staleness, or a positively known unmerged state. A failed fetch remains `unknown` in evidence and the confirmation is tied to that specific repository, base identity and failure reason. Revalidation retries refresh: if it succeeds and contradicts accepted evidence, invalidate; if it fails again with unchanged locally observable state and failure class, retain the explicit manual confirmation. Remote state cannot be proven unchanged while the network is unavailable; report this residual risk and never label it fresh or automatically integrated.

## Confirmations, preview and outcome

Always render the full ordered report and prospective remove plan before prompts. Human TTY collects one grouped manual completion confirmation naming every eligible unknown repository, then a distinct discard confirmation listing dirty/unpublished participants; decline either means no cleanup. For unknown completion, manually confirmed status is recorded as such, not `merged`. For dirty/unpublished non-TTY and JSON mutation, `--force` is required; it does not skip identity/evidence gates. The ordinary final remove confirmation and branch retention choices remain delegated to remove (do not double-prompt where safe); no silently supplied `--no-check-dirty`. `--dry-run` neither prompts nor invokes lifecycle hooks nor deletes branches/worktrees and is allowed to show blocked/unknown plans, but no plan may be labeled executable when its exact scope is not validated. Its only external reads are network queries; ephemeral fetch storage is disposed.

JSON uses the standard schemaVersion 1 one-document envelope, stable ordered repo records and reason codes, no spinners/prompts or hook text. Assessment `data` / failure `error.details` contains `target`, `dryRun`, `readiness` (`ready|blocked|unknown`), `repositories` (parent first, then configured-key bytewise order), `nonparticipants`, `blockers`, `warnings`, `confirmations` (`manualCompletion`, `discard`, `remove`: `not-needed|required|confirmed|declined`), `cleanupPlan` (remove's ordered pending operations, options and hook previews or null if invalid), and `cleanupResult` (remove's actual operations/hook outcomes/partial-failure details or null). Per-repository evidence exposes `worktreeState`, `branch`, `headOid`, `configuredBase` with source/ref/OID/freshness, `upstream` with counts/state, `integration` (`proven|not-finished|unknown|manually-confirmed`) and proof source/PR metadata, `dirty`, `unpublished`, `reasons`. Use null for unavailable facts, never fabricated zero; sort reasons and warnings by stable code/key, not completion order. Runtime timing can be omitted from the stable assessment. Top-level `ok: true` means assessment/preview completed or cleanup succeeded, not that blocked/unknown preview was ready; mutating blocked/unknown returns `ok:false` with the complete report. Proposed exits: `0` assessment preview (even blocked/unknown) or successful cleanup, `2` selection/confirmation required or declined, `1` evidence/config/revalidation errors, ineligible cleanup or partial remove failure. Distinct codes `FINISH_SELECTION_REQUIRED`, `FINISH_AMBIGUOUS_TARGET`, `FINISH_CONFIRMATION_REQUIRED`, `FINISH_DECLINED`, `FINISH_NOT_READY`, `FINISH_EVIDENCE_UNAVAILABLE`, `FINISH_PLAN_INVALIDATED`, `FINISH_REMOVE_FAILED`. Structured error carries report even on failure after target resolution. Non-interactive completion confirmation is deliberately deferred; no generic force/manual bypass.

## Remove boundary and concurrency

`remove` currently reruns only unplanned-descendant discovery after `pre-remove` hooks (source `repos/arashi/src/commands/remove.ts`, immediately following hook execution). That **does not** revalidate a finish assessment. Add an optional internal finish-specific pre-mutation callback to the existing remove executor, run after all `pre-remove` hooks succeed and after removal's descendant refresh, within an explicit finish/remove coordination barrier (the current remove source shows a post-hook descendant check, not a general lock; design must add synchronization or document the residual race) and **before the first** detach, worktree removal or branch deletion. The callback re-reads exact configuration bytes/policy, Git registrations and paths, all participant dirty/HEAD/branch/upstream/base remote identity and OIDs, PR identity and status where used, current remote refs (fresh refresh, including failures), and the complete closed remove plan/hook target set; compare against the accepted immutable assessment. Recompute completion and check consent remains applicable. Any discrepancy or failed local read returns a structured `FINISH_PLAN_INVALIDATED` with no destructive operation, retaining hook outcomes. Repeated remote/PR read failures may retain only the *same explicitly manually confirmed unknown* with unchanged locally observable identities and failure class; the report preserves uncertainty. Newly successful contradictory reads invalidate the plan. Also validate after finish confirmation and before entering remove, since remove may have its own prompt/hook gap. A callback scoped to finish preserves ordinary remove's behavior; invoking `remove` as a shell subprocess or just calling its public executor before hooks is insufficient. If a hook changes an already assessed file, branch, base ref, config or target, reject. Hooks may have side effects even when cleanup is aborted; report that explicitly. Revalidation cannot guarantee atomicity against arbitrary external writes after the final check; coordinate finish's new barrier with remove's descendant and per-operation protections rather than advertise perfect transactional isolation. Do not attempt rollback after partial removal; return remove's ordered ledger, failed descendants/ancestors and post-remove outcomes, preserving finish report and safe retry guidance.

## Design review checkpoints

Before code, independently review semantic evidence and remove architecture at exact design HEAD. Specifically resolve: (1) exact-path handoff without deleting unrelated branches, (2) preview's isolated fetch mechanics, (3) PR API pagination/head OID provenance, and (4) post-hook callback placement/lock boundary. If any cannot be implemented with the documented fail-closed behavior, revise design and revalidate/review at new HEAD rather than weakening proof. `openspec validate --strict` establishes only artifact structure, not semantic approval.
