# Part 1: Configuration Schema (D1)

## Overview

Arashi stores project-level configuration in `.arashi/config.json` at the repository root. This configuration controls worktree behavior, repository discovery, and automation settings.

## Configuration File Location

**Path**: `.arashi/config.json` (relative to project root)

**Creation**: Generated by `arashi init` command

**Format**: JSON with support for comments in examples (runtime parser strips comments)

## Configuration Schema

### Top-Level Fields

| Field | Type | Required | Default | Validation | Description |
|-------|------|----------|---------|------------|-------------|
| `version` | string | Yes | `"1.0.0"` | Semantic version format (x.y.z) | Config schema version for migration support |
| `repos_dir` | string | No | `"repos"` | Relative path, no leading/trailing slashes | Directory containing sub-repositories |
| `worktree_strategy` | string | No | `"same_branch"` | One of: `"same_branch"`, `"independent"`, `"prompt"` | Default branch naming strategy for sub-repos |
| `auto_setup` | boolean | No | `true` | Boolean | Whether to run setup scripts automatically after worktree creation |
| `discovered_repos` | object | No | `{}` | Map of repo names to RepoConfig | Auto-populated repository metadata |

### Nested Structure: discovered_repos

The `discovered_repos` field is an object mapping repository names to metadata objects. Each repository entry has the following structure:

| Field | Type | Required | Default | Validation | Description |
|-------|------|----------|---------|------------|-------------|
| `path` | string | Yes | N/A | Relative path from `repos_dir` | Path to repository directory |
| `default_branch` | string | Yes | N/A | Non-empty string | Default branch name (e.g., `"main"`, `"master"`) |
| `remote` | string | Yes | N/A | Valid git remote name | Primary remote name (typically `"origin"`) |
| `has_setup_script` | boolean | Yes | N/A | Boolean | Whether `.arashi-setup.sh` exists in repo |
| `git_url` | string | Yes | N/A | Valid git URL (https/ssh) | Remote URL for cloning/fetching |

**Note**: `discovered_repos` is auto-populated by `arashi init` and `arashi add` commands. Manual editing is supported but discouraged.

## Validation Rules

### Field-Specific Validation

1. **version**
   - Must match semantic versioning format: `^\d+\.\d+\.\d+$`
   - Currently supported: `"1.0.0"`
   - Future versions will trigger migration prompts

2. **repos_dir**
   - Must be a relative path (no leading `/`)
   - Must not contain `..` (no parent directory traversal)
   - Must not end with `/`
   - Must be a valid directory name for all supported platforms (Windows, macOS, Linux)

3. **worktree_strategy**
   - Allowed values: `"same_branch"`, `"independent"`, `"prompt"`
   - `"same_branch"`: All sub-repos use the same branch name as main repo
   - `"independent"`: Sub-repos stay on default branch
   - `"prompt"`: Ask user interactively for each sub-repo

4. **auto_setup**
   - Must be boolean (`true` or `false`)
   - Controls whether setup scripts run automatically
   - Can be overridden per-command with `--no-setup` flag

5. **discovered_repos**
   - Keys must be valid directory names
   - Keys must match actual subdirectory names in `repos_dir`
   - Values must conform to RepoConfig structure
   - `path` must be relative to `repos_dir`
   - `git_url` must be reachable (validated on `arashi add`)

### Cross-Field Validation

- All `discovered_repos[*].path` values must exist as subdirectories of `repos_dir`
- Repository names (keys in `discovered_repos`) must match directory names

### Validation Timing

- **On load**: Validate structure, types, and field constraints
- **On save**: Validate all fields and cross-field relationships
- **On command**: Validate command-specific requirements (e.g., repo exists before creating worktree)

## Default Values

| Field | Default | Rationale |
|-------|---------|-----------|
| `version` | `"1.0.0"` | Initial schema version; enables future migrations |
| `repos_dir` | `"repos"` | Convention over configuration; matches common project structure |
| `worktree_strategy` | `"same_branch"` | Most intuitive default; mirrors multi-repo workflow |
| `auto_setup` | `true` | Prefer automation; users can opt out with `--no-setup` |
| `discovered_repos` | `{}` | Empty until repositories are discovered via `init` or `add` |

## Version Migration Strategy

### Current Version: 1.0.0

This is the initial schema version. No migrations are needed.

### Future Migration Path

When schema changes are required:

1. **Bump version number** according to semantic versioning:
   - **Major**: Breaking changes (remove fields, change types)
   - **Minor**: Additive changes (new optional fields)
   - **Patch**: Documentation or validation clarifications

2. **Detection**: On config load, compare file `version` with supported versions

3. **Migration prompt**:
   ```
   Your config.json is version 1.0.0, but Arashi now uses version 2.0.0.
   Run `arashi migrate-config` to upgrade automatically.
   ```

4. **Migration tool**: `arashi migrate-config` command (future implementation)
   - Backup original config to `.arashi/config.json.bak`
   - Apply transformation (add fields, rename, convert types)
   - Update version number
   - Validate migrated config

5. **Backward compatibility**: Support reading older versions with warnings

### Migration Examples (Future)

**1.0.0 → 2.0.0** (hypothetical):
- Add field: `hook_timeout` (default: 300 seconds)
- Rename field: `auto_setup` → `enable_hooks`
- Remove field: `worktree_strategy` (always prompt now)

Migration logic:
```typescript
function migrate_1_0_0_to_2_0_0(config: Config_1_0_0): Config_2_0_0 {
  return {
    version: "2.0.0",
    repos_dir: config.repos_dir,
    enable_hooks: config.auto_setup,
    hook_timeout: 300, // new field with default
    discovered_repos: config.discovered_repos,
    // worktree_strategy removed
  };
}
```

## Design Decisions

### Decision: Semantic Versioning for Config Schema

**Choice**: Use semantic versioning (x.y.z) for config `version` field

**Rationale**: 
- Enables graceful migrations when schema evolves
- Clear communication of breaking vs additive changes
- Industry standard (package.json, docker-compose.yml)

**Alternatives Considered**:
- No versioning: Rejected (can't detect old configs)
- Integer version: Rejected (doesn't convey change severity)
- Git commit hash: Rejected (not human-readable)

**Consequences**:
- Must maintain migration paths between versions
- Breaking changes require major version bump and migration tool

### Decision: Relative Path for repos_dir

**Choice**: Enforce relative paths (no leading `/`)

**Rationale**:
- Portability across machines and users
- Enables sharing configs via git
- Prevents accidental reference to absolute system paths

**Alternatives Considered**:
- Allow absolute paths: Rejected (breaks portability)
- Both relative and absolute: Rejected (complexity)

**Consequences**:
- repos_dir must be under project root
- Cannot reference external directories

### Decision: Auto-Populate discovered_repos

**Choice**: Automatically populate `discovered_repos` via `init` and `add` commands

**Rationale**:
- Reduces manual configuration errors
- Single source of truth (git repo metadata)
- Simplifies user onboarding

**Alternatives Considered**:
- Manual editing only: Rejected (error-prone)
- Scan on every command: Rejected (performance impact)

**Consequences**:
- Config file changes when repos are added
- Users may need to commit config updates

### Decision: Default worktree_strategy = "same_branch"

**Choice**: Default to creating same-named branches in all sub-repos

**Rationale**:
- Most intuitive for feature branch workflows
- Mirrors typical multi-repo development patterns
- Can be overridden with `--interactive` flag

**Alternatives Considered**:
- `"independent"` default: Rejected (less common workflow)
- `"prompt"` default: Rejected (too interactive for automation)

**Consequences**:
- Users working with independent branches must change strategy or use flags
- Branch name collisions require interactive resolution

# Part 2: Type System (D2)

## Overview

This section defines all TypeScript interfaces and types used throughout the Arashi codebase. These types directly map to the configuration schema defined in Part 1 and provide compile-time safety.

## Type Definitions

### Core Configuration Interfaces

#### ArashiConfig

Main configuration interface matching `config.json` structure.

```typescript
/**
 * Arashi project configuration
 * Location: .arashi/config.json
 */
interface ArashiConfig {
  /** Config schema version (semantic versioning) */
  version: string;

  /** Directory containing sub-repositories (relative path) */
  repos_dir: string;

  /** Default strategy for branch naming in sub-repos */
  worktree_strategy: WorktreeStrategy;

  /** Whether to automatically run setup scripts after worktree creation */
  auto_setup: boolean;

  /** Auto-discovered repository metadata */
  discovered_repos: Record<string, RepoConfig>;
}
```

#### WorktreeStrategy

Type alias for allowed worktree strategies.

```typescript
/**
 * Strategy for determining sub-repo branch names during worktree creation
 */
type WorktreeStrategy = 
  | "same_branch"   // Use same branch name as main repo
  | "independent"   // Keep sub-repos on default branch
  | "prompt";       // Ask user interactively for each sub-repo
```

#### RepoConfig

Metadata for a discovered repository.

```typescript
/**
 * Metadata for a single repository within repos_dir
 */
interface RepoConfig {
  /** Path to repository (relative to repos_dir) */
  path: string;

  /** Default branch name (e.g., "main", "master") */
  default_branch: string;

  /** Primary remote name (typically "origin") */
  remote: string;

  /** Whether .arashi-setup.sh exists in repository root */
  has_setup_script: boolean;

  /** Git remote URL for cloning/fetching */
  git_url: string;
}
```

### Operation Logging & Rollback

#### OperationLogEntry

Entry in the operation log for rollback tracking.

```typescript
/**
 * Single entry in operation log for rollback support
 */
interface OperationLogEntry {
  /** Type of operation performed */
  type: OperationType;

  /** Operation-specific data for rollback */
  data: OperationData;

  /** Function to rollback this operation */
  rollback: () => Promise<void>;
}
```

#### OperationType

Types of operations that can be logged and rolled back.

```typescript
/**
 * Types of operations tracked in operation log
 */
type OperationType =
  | "worktree_created"    // Worktree was created
  | "branch_created"      // Branch was created
  | "directory_created"   // Directory was created
  | "setup_executed";     // Setup script was run
```

#### OperationData

Union type for operation-specific data.

```typescript
/**
 * Operation-specific data for rollback
 */
type OperationData =
  | WorktreeOperationData
  | BranchOperationData
  | DirectoryOperationData
  | SetupOperationData;

interface WorktreeOperationData {
  type: "worktree_created";
  repo_name: string;
  worktree_path: string;
  branch: string;
}

interface BranchOperationData {
  type: "branch_created";
  repo_name: string;
  branch: string;
}

interface DirectoryOperationData {
  type: "directory_created";
  path: string;
}

interface SetupOperationData {
  type: "setup_executed";
  repo_name: string;
  script_path: string;
}
```

### Error Handling

#### ArashiError

Custom error class with exit codes and git context.

```typescript
/**
 * Custom error class for Arashi operations
 * Includes exit codes and optional git command output
 */
class ArashiError extends Error {
  /** Exit code to return to shell */
  exitCode: number;

  /** Git command output (stdout + stderr) if applicable */
  gitOutput?: string;

  /** Original error that caused this error (if wrapped) */
  cause?: Error;

  constructor(
    message: string,
    exitCode: number = 1,
    gitOutput?: string,
    cause?: Error
  ) {
    super(message);
    this.name = "ArashiError";
    this.exitCode = exitCode;
    this.gitOutput = gitOutput;
    this.cause = cause;
  }
}
```

#### Exit Codes

Standard exit codes used throughout Arashi.

```typescript
/**
 * Standard exit codes for Arashi CLI

enum ExitCode {

  /** Operation failed due to error */
  ERROR = 1,

  /** User aborted operation (Ctrl+C, interactive cancel) */
```

### Type Safety Flow

1. **Configuration Loading**:
   - Read `config.json` → parse as `ArashiConfig`
   - Validate against schema → throw `ArashiError` if invalid

2. **Command Execution**:
   - Parse CLI arguments → map to command-specific `*Options` interface
   - Execute command logic → create `WorktreeInfo` objects
   - Log operations → create `OperationLogEntry` array

3. **Error Handling**:
   - Git command fails → wrap in `ArashiError` with `gitOutput`
   - Throw `ArashiError` → catch at top level
   - Return `exitCode` to shell

4. **Hook Execution**:
   - Build `HookContext` from command state
   - Execute hook scripts → capture `HookResult`
   - Non-zero exit → log warning, continue

## Design Decisions

### Decision: Interfaces vs Types

**Choice**: Use `interface` for object shapes, `type` for unions/aliases

**Rationale**:
- Interfaces are extendable (can add fields in future)
- Interfaces have better error messages in TypeScript
- Types are appropriate for unions (WorktreeStrategy, OperationType)

**Alternatives Considered**:
- Always use types: Rejected (less clear intent)
- Always use interfaces: Rejected (can't represent unions)

**Consequences**:
- Consistent pattern throughout codebase
- Easy to extend interfaces with new optional fields

### Decision: Exit Codes (0, 1, 2)

**Choice**: Use POSIX-standard exit codes

**Rationale**:
- 0 = success (universal convention)
- 1 = error (generic failure)
- 2 = user abort (distinguishes intentional cancellation from errors)

**Alternatives Considered**:
- Additional error codes (3, 4, 5...): Rejected (unnecessary granularity)
- Single error code (1): Rejected (can't distinguish abort from error)

**Consequences**:
- Shell scripts can detect user abort vs error
- Simple, predictable exit behavior

### Decision: Rollback Function Pointer in OperationLogEntry

**Choice**: Include `rollback: () => Promise<void>` function in log entry

**Rationale**:
- Strategy pattern: Each operation knows how to undo itself
- Type safety: TypeScript ensures rollback signature matches
- Simplicity: No need for separate rollback logic lookup

**Alternatives Considered**:
- Rollback function registry: Rejected (adds complexity)
- Switch statement on operation type: Rejected (less maintainable)

**Consequences**:
- Operation log entries are not serializable (contain functions)
- Rollback is in-memory only (suitable for Arashi's use case)

### Decision: Separate Command Option Interfaces

**Choice**: Define one interface per command (InitOptions, CreateOptions, etc.)

**Rationale**:
- Type safety: Each command gets exact options it supports
- Clear documentation: Options are self-documenting
- Extensibility: Easy to add command-specific options

**Alternatives Considered**:
- Single GlobalOptions interface: Rejected (not all options apply to all commands)
- No types, use `Record<string, any>`: Rejected (loses type safety)

**Consequences**:
- More interfaces to maintain
- Clear separation of concerns

### Decision: WorktreeInfo as Runtime Data (Not Persisted)

**Choice**: Do not persist WorktreeInfo in config.json

**Rationale**:
- Git worktrees already tracked by git (`.git/worktrees/`)
- Avoiding duplicate source of truth
- WorktreeInfo is derived from git commands at runtime

**Alternatives Considered**:
- Persist in config.json: Rejected (can become stale)
- Persist in separate database: Rejected (adds complexity)

**Consequences**:
- Must query git to get worktree list (slight performance cost)
- No risk of stale cached data

### Decision: HookContext via Environment Variables

**Choice**: Pass context to hooks via environment variables (ARASHI_*)

**Rationale**:
- Shell-agnostic (works with bash, zsh, fish)
- Standard pattern (npm, git, docker use env vars)
- No need for complex argument parsing in hooks

**Alternatives Considered**:
- Pass as CLI arguments: Rejected (requires parsing in hook)
- Pass as JSON file: Rejected (requires jq or similar in hook)

**Consequences**:
- Hooks must read environment variables
- Limited to string data (no nested objects)
